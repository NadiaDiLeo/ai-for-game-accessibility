    WHAT THIS TALK ASKS

    Can AI help collect evidence about a game’s accessibility, and where does that help stop?

    The evidence comes from two kinds of work. Experts audit games against accessibility guidelines, and players and studios publish what they find. Both take a long time by hand.

    Each part of the talk starts from a study done by people. Then I look at what a model could take over, and where it gets things wrong.

    AUDITING THE 2025 NOMINEES

    121 guidelines, two human evaluators, the first hour of play

    In 2025, five games were nominated for Innovation in Accessibility at The Game Awards: Assassin’s Creed Shadows, Atomfall, DOOM: The Dark Ages, EA Sports FC 26 and South of Midnight. With a second evaluator, I audited all five by hand against 121 Game Accessibility Guidelines.

    We first matched each feature in the studios’ accessibility materials to a guideline. Then each evaluator played the first 60 minutes of every game on PC, the first-time user experience (Barnett et al., 2018), and scored every guideline as pass (1), partial (0.5), fail (0) or not applicable. The scores agreed closely: Cohen’s κ = 0.92, where 0 is chance agreement and 1 is perfect. A future goal is to run audits like this at scale, with AI doing the first pass.

    I keep three measures apart: is a feature there, is it documented, and does it work for the players who need it? The audit measures the first two. A feature can be there and still fail: South of Midnight forgot custom key bindings at every launch.

    WHAT THE FIVE GAMES SHARE

    Every game scores lower on advanced guidelines than on basic ones. The drop is steepest for blind players: screen readers, voiced navigation and audio description are rare across the sample.

    Building access and documenting it look like separate efforts. FC 26 implements the least and documents the most; South of Midnight does the opposite.

    Some of the most innovative features still lack a relevant guideline, such as DOOM’s redesigned combat or South of Midnight’s Guiding Strand. A checklist has no row for them, and an automated checker built on that checklist would miss them too.

    POINTCHECK

    A web accessibility tester that looks at the rendered page

    PointCheck is an open-source tool by Brendan Works, featured by Ai2 in May 2026. It tests web pages against WCAG 2.1 and 2.2 at level AA.

    Existing rule-based tools (such as AChecker) focus only on a page’s code. PointCheck, instead, also looks at what appears on screen. It runs through each page and takes screenshots, finds the pixel coordinates of target elements, decides whether there is any issue, and writes a report.

    Every result keeps its screenshot and a confidence level. Checks that need human judgement, such as captions on live video, are left out, and the tool is designed to be self-hosted.

    FROM WEB PAGES TO PLAYABLE BUILDS

    Our audit cost each evaluator an hour of play and 121 judgements per game. More than 19,000 games were released on Steam in 2025.

    Games are harder to test than web pages: menus are drawn by the engine, the game state changes every frame, and many barriers appear only in play. Multimodal models still struggle to spot glitches in game scenes (Taesiri et al., 2024).

    A game version of PointCheck would drive a playable build the way our evaluators did: open the settings, change them, restart, play the first hour. It would attach frames and sounds to individual guidelines, as well as identify new, unseen guidelines.

    The output would be observations with evidence and a list of tests for an accessibility specialist. People still decide whether the game is accessible.

    A MODEL FOR GAMES

    A grant application for supercomputer time, under review

    Web pages now have tools like PointCheck. I have not found an open equivalent that checks a running game against the Game Accessibility Guidelines.

    To train one, I have applied for computing time with a project called A11YVLM. The application is under review, so no model has been trained yet.

    A vision-language model takes images and text as input. Shown a screenshot of a menu or of play, ours would name the barrier, cite the guideline, say which players it affects and suggest a fix.

    The models will be small, 2 to 9 billion parameters, so a studio can run them on its own machines without sending unreleased builds to anyone.

    HOW THE MODEL WOULD BE TRAINED

    The plan in the grant application. Nothing has been run yet.

    Training needs labelled examples, and accessibility experts cannot label tens of thousands of screenshots by hand. In this plan a large model drafts the labels, people check them, and the small models learn from the checked set.

    Two results on web pages suggest the approach is realistic. A vision-language agent found 86% of the barriers that experts had found, against 36% for the rule-based checker axe-core, although 44% of its flags were wrong (Mishra et al., 2026).

    Reinforcement learning raised a 4-billion-parameter model’s F1 score on interface violations from 36% to 84% (Mehta et al., 2026). F1 balances two things: how many real problems a model finds, and how many of its flags are correct.

    The first models look at still screenshots, so they cannot judge sound or timing. People playing the game still have to check those.

    WHAT 448 REVIEWS TALK ABOUT

    Can I Play That? accessibility reviews, 2019–2024

    Can I Play That? publishes accessibility reviews written largely by disabled players. I analysed 448 of them, published between 2019 and 2024 (Di Leo, 2025).

    GPT-4o extracted keywords from each review and labelled each one positive, negative or mixed. An embedding model and k-means clustering then grouped the keywords into six themes. Difficulty settings had the most keywords; visual accessibility had the widest gap between positive and negative ones.

    Each reviewer writes from their own needs. Someone who relies on subtitles may test every caption option and say nothing about motor access, so the corpus shows what mattered to the people who wrote it, which is not a complete inventory.

    HOW THE THEMES WERE FOUND

    The pipeline behind the six themes, step by step

    The theme charts count keywords, not reviews. One review can give many keywords, and they can fall into several themes.

    The method has limits worth knowing. All the reviews are in English. GPT-4o is a closed model that OpenAI keeps updating, so the same run cannot be repeated exactly. And k-means needs the number of groups chosen in advance, so that choice shapes the themes.

    The themes show what reviewers write about. They do not show which guidelines a game meets: that needed the mapping on the next page.

    Pipeline
    1. 1

      Collect A web scraper saved the full text of 448 accessibility reviews from Can I Play That?, published between 2019 and 2024.

    2. 2

      Extract keywords GPT-4o (OpenAI) listed each review’s accessibility keywords and labelled each one positive, negative or mixed. Of the models tested, it agreed most closely with a sample of reviews labelled by hand. Those same reviews then became the prompt’s few-shot examples: worked examples the model sees before the task.

    3. 3

      Embed OpenAI’s text-embedding-3-large turned each keyword into a vector: a list of numbers in which similar meanings sit close together.

    4. 4

      Cluster k-means sorted the vectors into groups of nearby points. I read each group to check and name it (the paper calls this qualitative supervision), which gave six themes.

    5. 5

      Draw the map t-SNE reduced the vectors to two dimensions for the cluster map. It only draws the picture; the groups come from step 4.

    FROM CHECKLISTS TO PLAYABILITY

    Mapping reviews onto the guidelines by hand

    I extended the corpus to 479 reviews (2019–2025) and mapped them onto the Game Accessibility Guidelines (Di Leo & Tarantino, 2026).

    For each game and each guideline, I read the review and chose yes (the feature is there and works) or no (it is missing or does not work), or left the cell empty when the review says nothing. With 120 guidelines, that is a matrix of more than 57,000 cells.

    The score multiplies the positive rate by a weight that grows with the number of tags, so a single enthusiastic mention cannot top the ranking.

    SCALING THE MAPPING

    A language model for the first pass, people for the rest

    Hand coding was feasible for this specific project, but it cannot keep up with every new review, studio accessibility page and patch note.

    A language model can do the first pass. For each passage it proposes a guideline, a label and a confidence, and quotes the words that support them. People check every uncertain label and a random sample of the rest.

    Language models already beat crowd workers on some annotation tasks (Gilardi et al., 2023), but their accuracy varies from task to task, so they must be validated against human coding first (Pangakis et al., 2023). In my study of 27,036 Minecraft Education reviews, an LLM reached κ = 0.71 against human coders, who agreed with each other at 0.74 (Di Leo, 2026b).

    The 479 hand-coded reviews can serve as the test set.

    TESTING THE FIRST PASS

    The planned experiment, before a model labels any new review

    Before a model labels new reviews, it should label the 479 I have already coded by hand, so that its answers can be compared with mine.

    Plain accuracy would mislead. Most cells are empty, because each review mentions only a few of the 120 guidelines, so a model that always said “not mentioned” would score high and find nothing. Cohen’s κ corrects for this, and precision and recall check the yes and no labels on their own.

    Models tend to overstate their confidence when asked for it (Xiong et al., 2024). Here it is measured instead: each review is labelled ten times, and confidence is the share of runs that agree.

    The hand coding was done by one person. A second coder should first label a sample, so the model is compared with a measured level of human agreement.

    Experiment setup (planned)
    task
    For every review and each of the 120 guidelines: yes, no or not mentioned, the same codes used by hand

    output

    runs
    Ten per review; confidence is the share of runs that agree
    test set
    479 hand-coded reviews × 120 guidelines = 57,480 decisions
    measures

    ONE RECORD FOR BOTH WORKFLOWS

    Audits of builds and mappings of existing games should produce the same record, so that their results can be compared.

    A record should include the game version, the guideline and the source, and quote or show the evidence. It answers four questions separately: does the guideline apply, is the feature implemented, is it documented, has it been confirmed in play? Confidence and reviewer notes stay attached.

    A single accessibility score would discard all of this. With the records, players can look up the evidence that concerns them, developers can find working examples, and researchers can compare releases over time.

    WHERE IT CAN GO WRONG

    • A model can miss barriers that appear after the first hour, or only under time pressure.Precaution Start some test runs from saves later in the game, and state in every report how much of the game was covered.
    • It can misread game state: in a single frame, a paused menu, a cutscene and live play can look alike.Precaution Give it a few seconds of video instead of one frame, and have it say which state it thinks it is looking at.
    • It can take a settings toggle for a feature that works.Precaution Count a feature as working only after it has been used in play and has survived a restart.
    • The sources have gaps. Speech guidelines are mentioned in 1.3% of the cases where they could be, so some disabilities and player groups are barely represented.Precaution Show how often each category is mentioned next to every result, and recruit testers from the groups the sources leave out.

    Any system needs traceable evidence and version history, then expert review and testing with disabled players.

    WHAT A REPORT CAN CLAIM

    It can claim

    “Feature X was observed in version Y, and here is the evidence.”

    “The studio’s accessibility page does not mention feature X.”

    “In N of these reviews, feature X is described as working.”

    It cannot claim

    “This game is accessible.”

    “Feature X works for every player who needs it.”

    “A guideline nobody mentioned causes no problems.”

    Try it: take one game or 20 reviews, choose ten basic guidelines, let a model propose labels with evidence, check every label by hand, and keep the records.
